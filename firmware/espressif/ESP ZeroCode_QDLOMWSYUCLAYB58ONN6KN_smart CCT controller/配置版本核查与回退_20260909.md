# 配置版本核查与回退（2026-09-09）

**最新进展：** 用户已烧录初版 V4 `Devices/1` 目录的 `fctry_cct_fixed_gpio4_cold_gpio5_warm.bin`（模式 1、Cold=4、Warm=5），并确认“ok了 已烧好”。本轮控制故障已获用户功能确认，固定此版本为当前可用基线；设备身份保留初版 V4，波形/负载验收仍待完成。后续工作见项目根目录 `项目进度.md`。下文保留此前排查过程与历史回退方法，不代表还需要回退原始 QD 或初版 V4。

修复前的用户测试记录：回退初版 V4 后，面板关闭只亮暖白；最暖、满亮度时只亮冷白；最冷、满亮度时暖白最亮，冷白也亮，两路同时点亮。更早的 QD 主固件 + swap 工厂配置曾出现能控制但暖灯不亮或冷暖异常。核查依据本地文件、原始 ZIP、历史日志及固件代码；尚未读取当前设备 Flash 或测量 PWM。

## 结论

原始文件没有丢失或被改坏。原始 QD（`temperature_mode=1、Cold=GPIO5、Warm=GPIO4`）是与图纸相符的历史基准，但本次 V4 实测提示当前物理颜色映射可能相反：GPIO4→冷白、GPIO5→暖白。必须用实际输出核实，不再把“原始 QD 的冷暖方向一定正确”作为结论。

模式 0 的亮度/色温双信号不适合按冷白/暖白两个功率通道直接驱动，能解释关灯后残留输出。若 GPIO4→冷白、GPIO5→暖白的推断成立，目标配置应是模式 1、Cold=4、Warm=5，即现有 QD swap 的字段值；但是这仍未解释此前 swap 暖灯不亮，需读回配置并核对真实输出。完整新记录和区分实验见同目录 `现象.md` 的“2026-09-09 补充”章节。

## 模式及修改完整性

对现有公共固件的配置解析代码核查：读取 `temperature_mode` 后执行“是否等于 0”，将结果写入硬件 CCT 功能位。因此本固件的模式 0 启用硬件 CCT；模式 1 关闭硬件 CCT，使用冷暖混光。这与《现象.md》中的模式差异记录一致。平台选项名称与 JSON 数字不要仅凭名称猜测。

参考：[乐鑫 lightbulb 驱动声明](https://github.com/espressif/esp-iot-solution/blob/release/v2.0/components/led/lightbulb_driver/include/lightbulb.h)、[乐鑫调光方案说明](https://docs.espressif.com/projects/esp-iot-solution/zh_CN/release-v2.0/electrical_lighting_solution/lightbulb_driver.html)。

swap 与原始 QD 只有 10 个字节不同：`0x264`、`0x280` 为 GPIO 数字；`0x64–0x67` 为条目 CRC；`0x7C–0x7F` 为配置数据 CRC。两个版本的 configuration JSON、数据 CRC 和条目 CRC 均校验通过。

进一步检查本地 Evaluation 公共固件的签名路径：其调用的函数在 `0x4200585E` 直接返回 0，随后进入 `Not verifying signature` 分支并返回成功。因此，对这份哈希确定的固件，原签名保留不是 swap 失败的首要解释；此结论不推广到其他固件或量产版本。

反汇编证据保存在 `debug-logs/2026-09-09-config-recovery/firmware-code-evidence.txt`。

## 只回退工厂配置

以下保留“恢复原始 QD 图纸基准”的操作方法，并非基于最新实测已经确定的最终修复。当前先按《现象.md》完成 V4 的区分实验和配置读回。

用你实际连接控制器的串口替换下方占位符。不要根据一个陌生的 USB 端口名称推定它就是控制器。

```bash
esptool \
  --port /dev/cu.你的串口 \
  --baud 115200 \
  --before no-reset \
  --after hard-reset \
  --connect-attempts 0 \
  write-flash \
  0x1F2000 "/Users/apple/Desktop/cctcontroller/firmware/espressif/ESP ZeroCode_QDLOMWSYUCLAYB58ONN6KN_smart CCT controller/Devices/1/fctry.bin"
```

出现 `Connecting...` 后按住 BOOT/GPIO9、按一下复位，连接成功后松开 BOOT。等待写入及哈希校验成功；需要时在释放 BOOT 后手动复位一次。

这次不要执行 `erase-flash`，也不要重烧 `0x0` 的 merged。fctry 分区为 `0x1F2000–0x1F7FFF`，文件大小 `0x6000`；`write-flash` 自动擦写对应的 6 个扇区，不覆盖相邻分区。

特别核查：这份 merged 长度为 `0x1FA000`，其证书区、fctry 区和 OTA 数据区均包含全 FF 填充。把整个 merged 写到 0x0 会覆盖这些区域。本目录旧版 `FLASHING_GUIDE_CN.md` 第 7.2 节虽然文字称“两个设备数据文件”，命令实际包含 merged，不能作为只更新工厂配置的命令。

## 回退后的判别步骤

1. 读取一次完整启动日志，确认 Product Config 实际为 `temperature_mode=1、gpio_cold_or_cct=5、gpio_warm_or_brightness=4`。此前项目串口日志实测波特率是 74880；烧录波特率 115200 是另一个设置。
2. 在 Apple Home 先开灯，亮度设为 100%；分别调到最冷、最暖，每次等待至少 2 秒（配置渐变时间 800 ms）。记录哪路灯带亮。
3. 关灯，检查两路输出。若有示波器，以控制器 GND 为参考，测 GPIO4/5 和相应 MOSFET Gate；不要把接地夹夹到 CW-/WW-。
4. 若 GPIO4 有随最暖设置变化的 PWM，而 U5 Gate 没有，检查 PWM1、R10 和焊接；若 U5 Gate 有合适的驱动而暖灯不亮，继续检查 U5、WW- 端子、供电与灯带暖白回路。不能仅凭一个测点就认定某元件损坏。
5. 若回退和 swap 两个版本中，始终是同一条物理灯带不亮，故障不太可能只由 GPIO 逻辑次序造成。需要同时比对实际加载的配置和两个 GPIO 的输出。

最初核查阶段仅整理恢复步骤；随后经用户要求另存生成上述 V4 修正版，原 BIN 均保留。用户已自行烧录并确认可用；助手没有连接串口、擦除或烧录设备。
